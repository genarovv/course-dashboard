## Постановка

Дашборд отвечает на вопрос «применяет ли студент приёмы курса», а не «лежат ли файлы». Источники: история коммитов MR, описания и обсуждения MR, дерево и содержимое найденных артефактов (включая найденные «не там» — D44). Результат — свод «приём × репозиторий» со статусами passed / failed / no_data и доказательствами (цитата, sha, номер MR).

## Изменения по слоям

### 1. git_client — два новых метода (оба хоста, MockTransport-тесты)
- `list_mr_commits(repo_url, git_host, mr_number)` → `[MrCommit(sha, message, position)]` в хронологическом порядке. GitHub: `GET /pulls/{n}/commits`; GitLab: `GET /merge_requests/{iid}/commits` (отдаёт в обратном порядке — развернуть). Ошибка — GitClientError, NFR-2 сохраняется.
- `list_commits(repo_url, git_host, ref, limit=100)` → `[MrCommit]` головы ветки (для доли коммитов с ID тикета). GitHub `GET /commits?sha=&per_page=`; GitLab `GET /repository/commits?ref_name=&per_page=`.
- `list_mr_changes(repo_url, git_host, mr_number)` → `[str]` путей изменённых файлов. GitHub `GET /pulls/{n}/files`; GitLab (API v4) `GET /merge_requests/{iid}/diffs` (fallback `changes` — deprecated, использовать diffs).
- Кодирование ref/путей — по правилу T73 (quote, safe='').

### 2. Модель: `practice_observation` (append-only журнал, миграция alembic)
Поля: id, sync_run_id FK, repository_id FK, check_key (str), status (enum: passed/failed/no_data), evidence (JSON: список {kind, mr_number?, sha?, quote?, path?}), observed_at. Как MrObservation: каждая проверка каждый обход — новая строка; текущее состояние = последняя строка по (repository, check_key). Мутации только через store (§3.5 — обновить перечень!).

### 3. Конфиг: секция `practice_checks` в config.yaml (реконсиляция НЕ нужна — проверки не сущности БД, читаются на лету как process_markers)
```yaml
practice_checks:
  - key: tests_first
    lesson: 11
    label: "tests-first: красная фаза отдельным коммитом раньше кода"
    kind: mr_commit_pattern
    pattern: "tests?[ -]first"
  - key: bug_repro
    lesson: 13
    label: "bug repro: тест-воспроизведение до фикса"
    kind: mr_commit_pattern
    pattern: "bug[ -]repro"
  - key: docs_sync
    lesson: 10
    label: "код и доки одним MR (или явный отказ с «потому что»)"
    kind: mr_docs_sync
    waiver_pattern: "докам обновление не требуется"
  - key: ticket_id_share
    lesson: 8
    label: "ID тикета в коммитах (трассировка код→задача)"
    kind: commit_id_share
    pattern: "(#\\d+|[A-Z]{1,6}-\\d+|T-?\\d{1,4})"
    threshold: 0.5
  - key: review_round
    lesson: 9
    label: "круг ревью в MR: обсуждение + вердикт «принято»"
    kind: review_round
  - key: public_url
    lesson: 15
    label: "публичный адрес прототипа в README открывается"
    kind: readme_url
  - key: env_example
    lesson: 15
    label: "образец переменных без значений (.env.example)"
    kind: tree_probe
    tree_patterns: ["**/*.env.example", "**/env.example", ".env.example"]
  - key: reviewer_config
    lesson: 9
    label: "агент-ревьюер: конфиг с контрольным списком"
    kind: tree_probe
    tree_patterns: [".claude/agents/*.md", ".opencode/agent/**", "agents/*.md"]
  - key: machine_lock
    lesson: 14
    label: "машинный замок: хуки или permission-конфиг"
    kind: tree_probe
    tree_patterns: ["hooks/*", ".husky/*", ".claude/settings.json", "opencode.json"]
  - key: deps_pinned
    lesson: 12
    label: "версии зависимостей запинены"
    kind: tree_probe
    tree_patterns: ["**/*.lock", "**/package-lock.json", "**/requirements*.txt", "**/pubspec.lock", "**/uv.lock"]
```
Плюс в СУЩЕСТВУЮЩИЕ механизмы (только конфиг, ноль кода):
- `process_markers` += `mutation` («Мутация:.*Поймал:»), `cause_evidence` («Причина:.*|Доказательство:.*» — два паттерна: cause «Причина:\s*\S», evidence «Доказательство:\s*\S»).
- `content_probes` += роль jtbd: трёхчастность «Когда.*(хочу|нужно).*чтобы» (contains); роль data_model: «erDiagram» (contains); роль prd: критерии приёмки «Given|Когда.*Тогда|- \[ \]» (contains).

### 4. Сервис `app/services/practice_checker.py`
`run_practice_checks(session, git_client, sync_run_id, repo, checks, mr_observations, tree)` — вызывается из обхода после `_observe_mrs` (деградация независимая, NFR-2: ошибка проверки → status=no_data + warning в лог, обход не валится). Виды:
- `mr_commit_pattern`: по смерженным MR репозитория (последние наблюдения) тянуть коммиты MR; passed — найден коммит с паттерном, стоящий НЕ последним (после него есть ≥1 коммит — след перехода красный→зелёный); evidence: mr_number, sha, message. Экономия API: MR, уже проверенные в прошлых обходах с тем же head_sha, не перечитывать (кэш по последней practice_observation с тем же evidence.head_sha — допускается упрощение: перечитывать только MR, чей updated_at новее observed_at последней проверки).
- `mr_docs_sync`: по смерженным MR: если в изменённых файлах есть код (не .md) — passed, когда есть и .md ИЛИ waiver в markers; иначе failed. MR только с .md — не считается.
- `commit_id_share`: list_commits(default_branch, 100), доля сообщений с паттерном ≥ threshold → passed; evidence: доля, примеры.
- `review_round`: по существующим MrObservation: passed — есть MR с reviewer_approved=true И ≥1 нотой до вердикта (использовать уже читаемые notes; если нот нет — failed «вердикт без обсуждения»).
- `readme_url`: в содержимом найденного readme-артефакта (через снапшот/чтение) первый https-URL вне github.com/gitlab; GET через httpx с таймаутом 10с; 2xx/3xx → passed; URL нет → no_data.
- `tree_probe`: паттерны по дереву default branch (глоб-транслятор `_glob_regex` переиспользовать); для env_example дополнительно прочитать файл: все непустые некомментарные строки — `NAME=` без значения → passed, есть значения ≥8 симв. после `=` → failed («в образце значения»).
- Бюджет API: не больше 3 MR на репозиторий за обход для mr_commit_pattern/mr_docs_sync (самые свежие смерженные); урезание — warning поимённо (образец D43).

### 5. UI (teacher-only, BR-4)
- `GET /practices` — таблица «репозиторий × проверка»: ✓/✗/— с title=evidence; строка репо кликом раскрывает evidence (цитаты, ссылки на MR). Ссылка из главной матрицы («приёмы») и обратно.
- В деле защиты (`/students/{id}/defense`) — блок «Приёмы курса»: passed списком одной строкой, failed — с доказательством, no_data — «нет данных: причина».
- Никаких вердиктов/оценок — только наблюдения с доказательствами (оценивает человек).

## Acceptance criteria (Given/When/Then — минимум по одному тесту на каждый)
1. Given смерженный MR с коммитами [«T5: tests first», «T5: impl»] → tests_first=passed с evidence.sha; Given один коммит «всё сразу» → failed.
2. Given MR с кодом и без .md и без waiver → docs_sync=failed; с waiver-фразой в описании → passed; MR только с .md → не учитывается.
3. Given 100 коммитов, 60 с «#12» → ticket_id_share=passed (0.6≥0.5); 30 → failed.
4. Given MR с notes=[замечание, «принято»] approved → review_round=passed; approved без notes → failed.
5. Given README с https://example.app и фейк-клиент сети 200 → public_url=passed; без URL → no_data.
6. Given .env.example c «KEY=» → passed; с «KEY=sk-abc12345» → failed.
7. Ошибка GitClientError в одной проверке → status=no_data, warning в лог, остальные проверки и обход живут.
8. Повторный обход без изменений MR — новые строки journal не дублируют чтение коммитов MR (кэш) — допустим тест на «не ходили в API» через счётчик фейк-клиента.
9. /practices отдаёт 200 залогиненному, 303 гостю; в таблице все репо реестра × все проверки конфига.
10. Пробы jtbd/data_model/prd и маркеры mutation/cause_evidence работают через существующие механизмы (тест конфига: ключи присутствуют и валидны).

## Ограничения, названные честно
- «Красная фаза» по порядку коммитов — слабый сигнал (порядок имитируем задним числом; состав файлов пер-коммит не тянем — дорого). В UI подпись «след, не доказательство».
- mr_commit_pattern смотрит ≤3 свежих смерженных MR — урезание логируется.
- Секрет-скан истории и health-проверка — вне этапа 1 (риски ложных срабатываний; в каталоге помечены).
