# ADR-007 — FR-12: наблюдение канала сдачи (MR) — второй домен наблюдения

- **Статус:** Proposed (ждёт взгляда CEO; решение «строить полный FR-12» принято на совещании 2026-07-28, этот ADR фиксирует «как»)
- **Дата:** 2026-07-28
- **Основание:** протокол `meetings/2026-07-28-приоритизация-проверки-заданий.md`, развилка 2 → решение CEO «полный FR-12 сейчас»; PRD FR-12 / US-B7.

## Контекст

С занятия 11 действует порядок сдачи: «работа = MR, доведённый до вердикта „принято" агента-ревьюера студента; кнопку merge нажимает преподаватель». Маркеры недель 6–7 объявлены студентам как машинная проверка и живут в описаниях MR. Продукт наблюдал только файлы default-ветки (D31–D32): сдавший через MR студент выглядел несдавшим (проверка 2026-07-28), маркеры проверялись вручную. Список драйверов D1–D39 датирован 09.07 и канала сдачи не содержит — дефект списка, а не предложения.

**Новый драйвер D40:** канал сдачи課а — MR (состояние, описание, обсуждение); источник — порядок сдачи занятия 11 (объявлен студентам, повторён на занятиях 12–13).

## Почему новая сущность, а не переиспользование ArtifactSnapshot

`ArtifactSnapshot` привязан к паре «занятие × роль артефакта» и отвечает на вопрос «существует ли документ». Наблюдение MR отвечает на другие вопросы («в каком состоянии процесс сдачи», «какие маркеры заполнены», «есть ли вердикт ревьюера») и не имеет ни занятия, ни роли. Насильственная упаковка MR в снапшот сломала бы И8/И9 и семантику матрицы. Симметрия с записями «почему не строим»: здесь — «почему строим».

## Рассмотренные варианты

- **А — только честная пометка** («канал сдачи MR, не наблюдается»). Честные плюсы: нулевая стоимость, ложное «нет» снято. Отвергнут как конечное состояние: объявленный студентам машинный контроль остаётся невыполненным обещанием курса. Принят как интерим до готовности FR-12.
- **Б — обход головы открытого MR без новой сущности** (снапшоты с ref ветки MR). Честные плюсы: артефакты студента видны, провенанс существующий, нет миграции; за него архитектор и финдир. Отвергнут решением CEO: не закрывает маркеры и вердикты — то, что объявлено студентам как контроль. Остаётся **вариантом отката**: если к 8.08 FR-12 не дошёл до зелёных тестов (триггер в протоколе).
- **В — полный FR-12: сущность MrObservation + чтение MR API** — принят.

## Решение

1. **Модель:** `MrObservation` — append-only журнал (категория 1 контракта store §3.5): `id, sync_run_id, repository_id, mr_number (iid/number), title, source_branch, state (opened|merged|closed), reviewer_approved (bool), markers (JSON: ключ маркера → найден/нет + цитата строки), head_sha, updated_at (у хостинга), observed_at`. Инвариант **И12**: `UNIQUE (sync_run_id, repository_id, mr_number)` — одно наблюдение MR за обход (DDL).
2. **Клиент:** `git_client` дополняется read-only методами: список MR/PR (открытые + смерженные), описание, обсуждения/notes. GitLab: `/merge_requests`, `/merge_requests/:iid/notes`; GitHub: `/pulls`, `/issues/:n/comments`. Те же rate-limit/ретраи (NFR-4). Scope токена — `read_api` (проверка — предусловие P3 плана).
3. **Обход:** шаг после артефактов, той же деградацией NFR-2 (ошибка MR-чтения — не крах обхода; исход честно фиксируется).
4. **Маркеры — конфигурация курса** (§3.4): секция `process_markers` в config.yaml: `key`, `pattern` (regex по описанию MR), `since_lesson`. Вердикт ревьюера: маркер «принято» ищется в обсуждении; **отрицательный контекст не считается принятием** — правило: совпадение допускается только как отдельная строка/начало строки вида «принято»/«APPROVE», вхождение внутри отрицания («не принято», «пока не…») отвергается тестируемым правилом.
5. **UI:** блок MR в карточке студента; колонка «процесс» в матрице; ячейка занятия с `submission_channel: mr` без артефактов показывает «сдача через MR» (интерим-часть, идёт первой).

## Негативные сценарии (обязательные тесты; вето тестировщика)

1. **Squash/rebase/amend/force-push в ветке MR:** порядок и даты коммитов не соответствуют хронологии работы → FR-12 **не делает выводов из порядка коммитов**; фиксируется состояние MR и head_sha. (Проверка «tests first раньше кода» остаётся справочной и выполняется по коммитам ветки только как best-effort с пометкой «после переписывания истории не доказуема».)
2. **Отрицание в тексте вердикта:** «пока не принято», «не принято, доработать» → reviewer_approved = false.
3. **MR закрыт без слияния** → state closed, из «готов к кнопке» уходит.
4. **MR пересоздан** (закрыт, открыт новый той же веткой) → два разных mr_number, оба в журнале.
5. **Force-push после вердикта:** head_sha изменился после «принято» → вердикт помечается устаревшим (reviewer_approved относится к head_sha на момент наблюдения).
6. **0 MR в репозитории** → пустой список, не ошибка.

## Последствия

- Плюсы: объявленный студентам контроль наблюдается инструментом; J3 закрывается при новом порядке сдачи; журнал переживает удаление веток.
- Цена: вторая доменная сущность и миграция (с работающим downgrade — вето девопса); +2–4 вызова API на репозиторий за обход (лимиты — «требует ручной проверки» из протокола); сложность правил вердикта.
- Несогласные (из протокола, не удалять): финдир — база «MR у 1 из 9» узка для самой дорогой работы списка; тестировщик — проверки порядка коммитов хрупки по природе (учтено: выводов из порядка не делаем).

## Триггеры пересмотра

| Решение | Пересмотреть, если… |

| Полный FR-12 | к 8.08 обход с MrObservation не зелёный → откат на вариант Б + пометка |
