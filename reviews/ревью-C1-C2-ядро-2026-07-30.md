## Что проверено и сошлось

**Контракт §5.2 (дословно):**
- `ensure_verdict`: `find_verdict_by_quadruple` → LLM → `register_verdict ok/break/deferred` — порядок и ветвления §5.2 воспроизведены. «Если найден И verdict != 'deferred' → return» реализовано конструктивно: `find_verdict_by_quadruple` (store.py:339-350, существующий код) сам фильтрует `verdict != deferred` — deferred не блокирует пересчёт (тест `test_deferred_verdict_is_recomputed`, при этом старый deferred остаётся в журнале — append-only И5 соблюдён).
- `validate_llm_response`: обязательные поля, домены ok/break и high/medium/low, целостность `checked == found + excluded + lost`, points ≤5, fence-извлечение, нормализация регистра — всё из §5.2 + доработки C3. Bool-счётчики отклоняются (`type(c) is int`, llm_client.py:104) — ужесточение из C3 сохранено в коде (но см. находку 1 про тесты).
- Ровно 1 повторный запрос (`for _ in range(2)`, llm_client.py:131), без эскалации промпта — буква решения v3. Двойной провал → None → deferred(parse_error) у вызывающего; `httpx.HTTPError` → `LLMUnavailableError` → deferred(llm_unavailable). Оба пути протестированы на обоих уровнях.
- Промпт-каркас v1 канонически переехал в клиента, дубли в `evals/mini_eval.py` удалены (промпт, валидация, ретрай) — «один факт — в одном месте» для промпта восстановлен; мини-эвал прогоняет golden set через `LLMClient.check_coherence` (AC #35), контрольный прогон по CHANGELOG — вердикты идентичны прямому (GS 2/2).

**Слои §3.2 и контракт store §3.5:**
- `llm_client` не знает о моделях данных: вход — сырые тексты, выход — dict. ORM/store не импортируются. (§3.2 упоминает «Pydantic-схемы» на границе — dict слабее, но модели данных граница не протекает; типизированная схема — рекомендация, не находка.)
- `coherence_analyzer` (service) → store + clients + models; `PendingPair` импортируется из соседнего сервиса — «services могут вызывать другие services», циклического импорта нет (воркер инъецируется в `run_sync`, оркестратор ядро не импортирует).
- store расширен **только** четырьмя точечными `find_*` (store.py:449-464, `session.get` по PK) — категория «журнал», никаких новых `update_*`, `delete_*` нет. Контракт «ровно 5 update_*» не тронут.
- `admin.py`: `get_llm_client` как FastAPI-зависимость (подменяемость в тестах), сборка воркера — композиция, не бизнес-логика; `SessionLocal` из store — существующий паттерн (`app/routes/__init__.py:6`).
- Без ключа DeepSeek воркер = None, пары честно остаются «проверяется» (оба wiring-теста).

**Инварианты и data-model:**
- **И2** — проверяется кодом до git/LLM-вызовов (`_check_i2`): оба снапшота найдены, `repository_id` обоих равен репозиторию пары, роли (source, target) дословно сверяются с ребром. Оба сценария нарушения протестированы, записи в БД при нарушении нет.
- **И3** — гонка двойной вставки четвёрки закрыта дважды: Lock сериализует воркеры в процессе, а повторный `find_verdict_by_quadruple` в свежей сессии воркера ловит вердикт, закоммиченный параллельным сводом (второй воркер вернёт существующий, LLM не вызовет). Partial unique index — последний рубеж.
- **Д25 («не мигаем»)** — существующий валидный вердикт возвращается без LLM-вызова (тест: `llm.calls == []`).
- Тексты читаются из git по `file_path @ source_commit_sha` — контент пары immutable (sha пиннит содержимое), совпадение с хешами четвёрки гарантировано конструктивно; контент не храним (С4). CHECK-констрейнт снапшота гарантирует sha для всех статусов кроме not_found, а в пары не попадают снапшоты без `content_hash` — фолбэк `or repo.default_branch` (coherence_analyzer.py:89,93) на практике мёртвый (см. находку 8).

**Деградации и надёжность:**
- Git-сбой → `return None` **без записи** — кейс, которого в §5.2 нет: осознанно (не вина модели, deferred_reason для него нет в enum), задокументирован в докстрингах модуля и функции + CHANGELOG + тест `test_git_failure_writes_nothing`. Пара без вердикта автоматически вернётся следующим сводом (§5.1). Решение верное; в §5.2 ARCHITECTURE не внесено — см. находку 5.
- Воркер: собственная сессия на пару, commit только при не-None, откат неявный при закрытии сессии, `log + continue` — падение одной пары не валит остальные fire-and-forget задачи. Приемлемо для свода; но И2-ValueError тоже проглатывается — см. находку 3.
- Сериализация Lock — трейд-офф задокументирован в докстрине и CHANGELOG («единый writer SQLite»); фактический скоуп шире заявленного — см. находку 7.

**Секреты и детерминизм:**
- Ключ API — только в `Authorization`-заголовке из settings (NFR-3); ни один `logger.*`, ни `LLMUnavailableError(str(exc))` (httpx-строки содержат метод+URL, не заголовки), ни отчёт мини-эвала ключ не печатают. Утечки нет.
- `temperature=0.0` + `response_format: json_object` — детерминизм прогона (канон Б1), закреплено тестом `test_check_coherence_valid_first_try`. Ретрай тем же промптом при temperature=0 почти наверняка повторит детерминированную ошибку — соответствует букве §5.2 («1 повторный запрос»); главные детерминированные классы (регистр, fence) сняты нормализацией ещё в C3, остаточный кейс уходит в deferred и пересчитывается сводом. Известное ограничение, не находка.

**Tests first (история коммитов):**
- C1: `3afe809` — только `tests/test_llm_client.py` (модуль пуст на main → ImportError → красные), реализация следом. Честно.
- C2: `f67cba0` — только `tests/test_coherence_analyzer.py` (красные: модуля нет), реализация следом; в имплементационном коммите **добавлены** (не изменены) wiring-тесты в тот же файл, что оформлено `tests-change:`-пометкой с обоснованием («шпион run_sync вместо гонки с fire-and-forget loop» — резонно). Гейт H1 соблюдён формально и по духу.
- Качество тестов: поведенческие, фейки на контрактных границах (FakeGit/FakeLLM/SlowLLM), свежая alembic-БД на тест, проверяют «что», не «как». `test_worker_serializes_writes` реально различает наличие/отсутствие Lock (без него оба воркера прошли бы D25-проверку до коммита и вызвали LLM параллельно).
